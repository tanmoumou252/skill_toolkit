# ZCode-Plan-First：计划文件先行 × 子代理落盘调度（自足完整版）

<SUBAGENT-GUARD>
先判定你的运行角色，再决定本 skill 对你是否生效。**ZCode 平台事实：所有自定义代理均为子代理，不存在自定义主代理**——"主/子代理"判定在本平台不适用，一律按下列角色判定：

- **你是 `plan-writer-subagent-sp`（计划撰写与回灌子代理）** → 本 skill 对你**全量生效，严禁忽略**：物理落盘 `.kilo/plans/`、计划正文纯净性、授权门槛声明与闸门转达、账实守恒回灌等条款都是你的执行纪律。调度类条款（强制分派、【物理在场】校验、多轮交叉复审）是父会话的纪律，你无需执行，但必须配合（如接受缺盘驳回重派）。
- **你是 `plan-reviewer-subagent-sp` / `pr-reviewer-subagent-sp`（复审子代理）或其他任何子代理** → 本 skill **整体不适用，立即忽略其余全部内容**：直接执行父会话分派的复审/任务指令；不进入计划文件流程，不等任何授权词（复审报告按分派要求落盘除外）。
- **你是 ZCode 主会话**（内置任务模式编排者，拥有交互式用户通道，能等到打字的用户）→ 本 skill 全量适用：强制分派、禁止内联、【物理在场】校验闭环与多轮交叉复审都是你的调度纪律。

非 ZCode 平台借用本 skill 时，恢复通用主/子判定：拥有交互式用户通道的主代理全量适用；被父代理分派、无用户通道的子代理整体忽略，直接执行分派任务。
</SUBAGENT-GUARD>

## 定位（自足声明）

本 skill 自足内含"计划文件先行、执行授权隔离"的**完整授权语义**，不依赖、不引用任何其他技能即可独立运行——单装本 skill 即获得三闸门分离、四阶段状态机、ExitPlanMode 例外判定与授权词严格解释的全部约束。在通用语义之上，叠加 ZCode 平台专属调度细节：计划由分派的 Writer 子代理经受控写工具 `write_scoped_file`**物理落盘**、复审由独立 Reviewer 子代理承担、父会话以【物理在场】校验为唯一硬闸门。**生效对象仅两类**：ZCode 主会话（调度纪律）与 `plan-writer-subagent-sp`（写作纪律）；其余角色见文首 `<SUBAGENT-GUARD>` 直接忽略。

## 触发条件

用户请求属于会改变工作区状态的实现任务（创建/修改/删除文件、改配置、跑测试/构建/部署、修 bug、重构、写文档、运行验证），且你是 ZCode 主会话（任务模式）或 `plan-writer-subagent-sp` → 适用本条。纯粹只读问答不触发。主会话处于原生计划模式（plan mode）时同样强制适用——进入计划模式的第一动作即枚举子代理清单并分派 Writer 落盘，而非按宿主内置流程内联撰稿。Writer 子代理侧重其中的落盘纪律与正文纯净性条款，调度条款由父会话承担。

## 硬闸门（HARD-GATE）

本 skill 约束的是工作流边界，不是建议。任何实现任务都必须按以下顺序处理：

1. 只把实现计划经分派的 Writer 子代理**物理写入**当前工作区 `.kilo/plans/`，并由父会话在磁盘上校验成功（【物理在场】校验）。
2. 等待用户审批已经落盘的计划内容；审批不执行计划。
3. 等待用户在后续消息中再次明确授权执行指定计划；这才允许修改目标文件、运行测试或构建。
4. 执行完成后，继续等待独立的 Git 提交、推送或合并授权。

计划文件写入授权永远不等于计划内容执行授权。不能因为一次工具权限点击、计划模式退出、计划审批或模型自己的判断而跳过闸门。

**角色例外**：生效对象见文首 `<SUBAGENT-GUARD>`——ZCode 平台按角色判定而非主/子判定：`plan-writer-subagent-sp` 全量受本 skill 约束（写作纪律部分）；Reviewer 与其他子代理整体豁免，直接执行分派任务，无需任何授权词。

## 适用范围

触发本 skill 的任务包括但不限于：

- 创建、删除、移动或重命名文件和目录。
- 修改源代码、配置、文档、数据库、前端资源或构建产物。
- 修复 bug、实现功能、重构、迁移、升级依赖或调整运行行为。
- 运行与实现相关的测试、构建、格式化、服务器、部署或外部 API 操作。

纯粹的只读问答、代码搜索、解释现有实现、查看状态或用户明确要求只读检查时，不必伪造实现计划；一旦任务需要写入或执行，就必须触发本流程。

### 流程产物豁免（快通道）

当任务的**最终产物本身就是** `.kilo/plans/` 下的流程文档（计划、复审报告、PR 审查报告、合并记录等）时，主会话直接分派对应子代理（`plan-writer-subagent-sp` / `plan-reviewer-subagent-sp` / `pr-reviewer-subagent-sp`）落盘，父会话以【物理在场】校验闭环；**不为此类产物另起计划、不走 ExitPlanMode**。配套约束不变：分派 prompt 必须声明唯一写入路径，越界即驳回重派。

**计划模式冲突裁定（快通道专款）**：
1. 计划模式拦截的对象是主会话"本人直接写"，这是设计预期而非障碍：主会话对任何**计划、复审报告、PR 审查报告、合并记录等**写入被拦的唯一正确响应就是分派 **对应子代理** 落盘。
2. 快通道分派不是"执行任务"，而是计划阶段自身的产物落盘，与计划模式"禁止执行"不构成冲突。
3. 因此快通道任务禁止调用 ExitPlanMode、禁止就此询问用户；即便宿主计划模式工作流提示"回合只能以 AskUserQuestion / ExitPlanMode 结束"，以"分派 → 【物理在场】校验 → 文字汇报"结束回合即为合规结束。
4. 快通道只豁免**本工作区**产物落盘：任务夹带的其他 **状态变更操作**（git fetch、装依赖、改代码等）或工作区外变更主会话被拦时，**禁止**分派子代理代行。
5. 产物落在代码/配置区的实现任务不受本款影响，仍走原四阶段 + ExitPlanMode。

### 两类任务分流

- 改工作区真实内容（代码、配置、业务文档、测试构建）→ 计划先行，四阶段状态机照旧。
- 产出流程治理文档（产物落在 `.kilo/plans/` 下）→ 走"分派即执行"快通道。

风险模型差异：前者的兜底是事前审批；后者的兜底是物理校验 + 驳回重派——报告可逆、可重派覆盖，故无需事前审批。

本节为"硬闸门（HARD-GATE）"第 1 步与"触发条件"节所称"实现任务"的显式例外：流程产物快通道任务不属于该两节所述的实现任务，其余任务不受本节影响。

## 四阶段状态机（ZCode 版）

```text
用户提出实现任务
        |
        v
DRAFTING_PLAN
  主会话分派 Writer 子代理起草 -> 派发 Reviewer 独立复审 -> Writer 回灌终稿
  禁止执行计划中的任何操作
        |
        | 终稿计划与复审报告物理落盘，并通过父会话【物理在场】校验（Read/Glob 确认）
        v
PLAN_SAVED
  通过 ExitPlanMode 呈报终稿计划路径与摘要，等待用户审阅
  禁止执行计划中的任何操作
        |
        | 用户明确批准已落盘的计划内容
        v
PLAN_APPROVED
  报告"计划已批准，仍等待执行授权"
  禁止执行计划中的任何操作
        |
        | 用户在后续消息中明确指定该计划并授权执行
        v
EXECUTING
  只执行指定计划列出的操作
        |
        | 任务完成，且未获 Git 授权
        v
AWAITING_GIT_AUTH
  禁止 commit、push、merge 和其他集成操作
```

不存在"审批并执行"的合并状态。即使用户在一句话中同时说了"同意并执行"，也必须先确认计划已真实落盘，并把计划审批和执行授权记录为两个独立事件；不得在同一轮凭推断直接执行。

## 阶段规则

### 1. DRAFTING_PLAN：只落盘计划文件

- 主会话先读取必要的代码、文档和工作区状态理解范围（只读操作不算执行），随后按"强制分派"节分派 Writer 子代理；仅当枚举清单确认无 `plan-writer-subagent-sp` 时才允许主会话走兜底路径自行撰写。
- 计划必须真实写入当前工作区根目录下的 `.kilo/plans/`，不能只写在聊天消息、工具结果或临时变量中。
- 文件名使用时间戳和主题，例如 `.kilo/plans/20260731153000-add-export-plan.md`。
- 计划至少说明目标、涉及文件、实施步骤、验证方式、明确排除项和成功标准。
- 计划阶段唯一允许的文件写操作是当前任务的计划文件。不得创建计划中提到的目标文件，不得改源码、配置、文档、数据库或构建产物。
- 需要请求工具权限时，权限说明必须精确限定为"写入/更新这一个 `.kilo/plans/` 计划文件"；不能把它描述成允许执行计划。
- Writer 回报后，父会话立即 Read/Glob 校验文件真实存在并核对内容；校验失败即驳回重派，停留在本阶段，不得转入执行。
- 不得在计划文件落盘并校验通过前请求计划审批。

### 2. PLAN_SAVED：只等待计划审批

- 向用户报告真实的计划文件路径和校验结果，并明确目标文件尚未修改。
- 路径输出格式：使用以 `.kilo/plans/` 开头的工作区相对路径（例如 `.kilo/plans/20260731150000-fix-plan-path-display.md`），不添加前导 `./`，并包裹在行内代码中。避免生成会被界面标记为 `[blocked]` 的本地绝对路径 Markdown 链接。只有用户明确要求时才使用绝对路径。
- 等待用户审阅计划内容。用户说"同意""可以""approved""没问题"等，只能转换到 `PLAN_APPROVED`。
- 计划审批只表示用户接受计划文本，不授权计划中的创建、修改、删除、移动、测试、构建、服务器或外部 API 操作。
- 用户请求修改计划时，只能重新分派 Writer 修改该计划文件；修改后重新校验并重新等待审批。
- 用户说"继续""好的"但没有明确审批计划时，不要擅自推进状态。

### 3. PLAN_APPROVED：只等待独立执行授权

- 明确告诉用户：计划已经批准，但还没有执行授权。
- 必须等待后续单独消息，且消息必须明确要执行哪个已保存计划，例如"执行 `.kilo/plans/20260731153000-add-export-plan.md`""开始执行刚才的计划"。
- "ExitPlanMode 已批准""计划批准""工具允许调用 Write""approved"或"同意"本身都不能转换到 `EXECUTING`。
- 如果用户在计划尚未审批时直接说"执行"，先要求审批已落盘计划；不能把执行请求反向当作计划审批和执行的合并授权。
- 执行授权只覆盖指定计划中的任务，不覆盖目录中其他计划，不覆盖未列出的操作，也不覆盖 Git 集成。

### 4. EXECUTING：严格按指定计划执行

- 执行前再次读取并确认指定计划路径，避免按"最新文件"或相似文件名猜测。
- 只修改计划列出的文件；计划未列出的额外变更必须先停下并获得新的计划/授权。
- 按计划顺序执行，每完成一个 Task 就更新计划中的勾选状态；更新计划本身不扩大执行范围。
- 运行测试、构建、启动服务、外部 API 或删除/移动操作前，检查计划是否明确列出；危险或不可逆操作仍需单独确认其安全范围。
- 真实报告命令和结果。失败、取消、权限拒绝或跳过都必须如实说明，不得声称已完成。
- 完成任务后进入 `AWAITING_GIT_AUTH`，不要自动提交、推送、合并或创建 PR。

### 5. AWAITING_GIT_AUTH：独立 Git 闸门

- `commit`、`push`、`merge`、rebase、创建 PR 或发布外部内容都需要用户明确的 Git/集成授权。
- 执行授权不等于提交授权。用户未明确授权时，只能报告工作区状态和验证结果。

## 授权词的严格解释

| 用户输入或宿主事件 | 允许的动作 | 不允许的动作 |
|---|---|---|
| 工具权限弹窗允许写计划 | 写入指定 `.kilo/plans/*.md` 并校验 | 执行计划 Task、改源码、跑测试、构建 |
| `ExitPlanMode` 返回批准 | 结束计划编写。仅当当前系统提示词**逐字含完整标记** `Read this file first and treat it as the source of truth for implementation`（缺此串不授权）时标记构成授权；ZCode 同对话执行不含标记，须等明确执行命令 | 在当前对话执行计划内容 |
| "同意""可以""approved" | 记录计划审批 | 创建目标文件、改代码、测试、构建 |
| "执行指定计划"或"开始执行刚才的计划" | 进入 `EXECUTING` | 执行其他计划、Git 集成 |
| "提交""push""commit" | 仅在执行完成后进入 Git 授权处理 | 未经确认修改其他文件或发布内容 |
| "停""不要执行""先不执行""等等" | 立即停止一切非只读操作 | 重试写入、继续执行或猜测用户意图 |

如果用户的词语存在歧义，选择更严格的解释并询问，不要扩大授权范围。

## 中断与异常

- 计划文件路径不明确、写入失败、读取失败、内容不完整或校验失败时，停留在计划阶段并报告原因；Writer 产物不在盘按"子代理产物落盘校验闭环"节驳回重派。
- 用户撤回、暂停或使用中断词后，立即停止；不要通过重试、换工具或改写其他路径绕过拒绝。
- 权限闸门拒绝（宿主弹窗被拒、deny 命中或终端工具未注入）与用户拒绝同级：同一意图至多一次改用内置只读工具（Read/Grep/Glob）的改道；第二次受阻立即停手，如实报告 BLOCKED 与原始命令及拒绝形态。严禁以语法变体、拆分拼接或更换命令行工具反复探测闸门边界——探测行为本身视同越权。
- 已存在的旧计划不会自动执行。用户必须明确指定计划文件；多个候选计划存在时必须询问。
- 绝不使用 `git reset --hard`、`git checkout --`、`git clean` 或其他回滚/清理命令来"清理"状态：Git 写命令一律由人类在宿主终端执行，Agent 只输出命令原文（即便用户明确要求也不代跑）。需要人类清理现场时，提示其先运行 `git status --short -uall` 通读并区分 `??`／` M`／`M ` 三态、确认清理半径，再优先使用可逆通道 `git stash push -u -m "discarded-本计划标识"`；仅在确认无保留价值时才执行 `git checkout -- .` 与 `git clean -fd`。
- 不要删除或覆盖用户已有的计划、源码或配置；如目标文件已存在且不确定归属，先读取并报告。

## 回灌与重派

**平台事实**：计划模式下宿主拦截 `SendMessage`（无法给已存在的子代理续发指令），但放行 `Agent` 分派；这是宿主设计而非异常。遇到需给已存在子代理续发指令（回灌 E 清单等）的场景时，预期行为是**重新分派全新 Writer**，不视为流程故障、不做绕行尝试。该口径已由用户在本工作流会话中亲口确认为宿主客户端设计（计划模式不放行 SendMessage 属有意限制），并经会话实测（SendMessage 被宿主拦截、Agent 分派可用）。

**重派降本要求**：回灌分派 prompt 必须自包含——E 清单全文内联（编号、严重度、证据 `路径:行号`、处置建议）+ 目标文件唯一路径 + "只允许编辑该文件"限定，使新 Writer 无需读复审报告原文即可一次改对。

**正面理由**：重派模式读取磁盘现状而非对话转述，回灌质量更可靠。

## ExitPlanMode 执行流（ZCode 同对话特性）

**指针纪律**：`ExitPlanMode` 的 plan 参数只允许携带：计划文件路径 + 一句话目标 + 分批摘要 + 三闸门声明。严禁在 plan 参数中内联计划正文、Anchor/Replacement 逐字终稿或任何本应落盘的内容——计划全文的唯一权威载体是磁盘上的 `.kilo/plans/` 文件，审批与执行都只认落盘文件。

**标记判定（自包含）**：当且仅当**当前对话系统提示词中逐字出现完整标记** `Read this file first and treat it as the source of truth for implementation` 时，该标记构成执行授权，直接读取计划文件并开始执行，不得要求再次明确授权。判定只看"此刻系统提示词里是否真的含这串完整标记"——不看文件名、不靠编号、不凭推断；缺此完整串即不生效。

**ZCode 主流场景**：`ExitPlanMode` 仅退出计划模式、在**同一对话**内继续、系统提示词**不含**上述完整标记——因此 **ExitPlanMode 批准不构成执行授权**，必须等待用户在下一条消息中明确执行授权（如"执行此计划"）。同时，宿主在计划批准后可能自动切到 YOLO 等权限档位；档位变化不构成执行授权以外的任何额外授权，Git 集成仍需单独授权。

**计划头部声明**：经本 skill 流程（非标记注入的新对话）交付的计划，文件头部必须逐字包含授权门槛声明：*本计划文件本身不等于执行授权；计划审批、执行授权、Git集成始终是三个独立闸门。* 仅当系统提示词逐字含完整标记（真·新对话执行流）时，计划文件**不得**再写该声明（两者矛盾）；Git 操作在任何流中都需独立授权。

## 强制分派（可观测触发条件）

1. 先调用代理/模式列表接口**逐字枚举**可用候选（子代理类型 / 主代理模式）。
2. 只要枚举清单中真实存在 `plan-writer-subagent-sp`：

## 禁止内联

ZCode 主会话（任务模式）**禁止在上下文内联撰写计划正文后弹 ExitPlanMode/等待审批**——这等于绕回 ZCode 原生计划模式（产物不留盘、批准即脱缰执行）。主会话亦禁止经 MCP 写工具直写产物（MCP 写面为蜜罐引导闸：main 恒按 plan 引导分派子代理、subagent 恒拒）。计划正文只允许由分派的 Writer 子代理经受控写工具 `write_scoped_file` 物理落盘；主会话只发分派 prompt（目标/路径/证据指针，不复述规范全文），不做计划内容撰稿人。

## 子代理产物落盘校验闭环（父会话唯一硬闸门）

对任何 Writer/Reviewer 子代理的回报：
1. 先做【物理在场】校验：用 `Read`/`Glob` 确认其声称落盘的产物真实存在于磁盘（主计划 `.kilo/plans/*.md`、独立影子对比计划 `.kilo/plans/review/<主计划文件名>-shadow-plan.md`，以及已生成时的 `.kilo/plans/test-evidence/` 证据文件）。
2. 文件缺失，或回报只在聊天上下文贴了报告正文而没落盘 → 判定该子代理本轮**未完成**，驳回回报并要求补写落盘后重验；禁止把上下文里的报告正文当作已落盘产物。
3. 校验通过后，才消费其 E 清单与计数进入合并/回灌。

**层级与权威**：父会话【物理在场】校验是**唯一可客观验证的硬闸门**，必须无条件执行；子代理提示词里的"回报只许摘要"只是行为引导（第一层），父会话不得因第一层存在而省略本层校验。

## 单一独立影子代理重写对比计划与镜像对账闭环

父会话对 `plan-reviewer-subagent-sp` 实行**首波单一影子代理独立重写对比计划与镜像差集对账**（首波并发 Reviewer 恒为 1 个，彻底废除首波同质化并发多 Reviewer 走过场与互相背书）。执行以下核心纪律：
1. **背靠背独立解题与镜像对账**：首波恒定只分派 1 个 Reviewer（报告路径统一指定为 `报告路径：.kilo/plans/review/<主计划文件名>-shadow-plan.md`）；Reviewer 先不读主计划，从零独立起草完整影子计划，随后读取主计划生成双卷镜像差集对账表。分派 prompt 同时声明测试基线文件路径供 Reviewer 先读基线再复跑对照。
2. **主代理强制仲裁铁律**：主计划回灌时严格执行硬规则：① Files 清单差集默认 Critical（必须二选一：补正吸收或证据反驳，严禁视而不见）；② 步骤覆盖差集默认 Important（核实必要性后吸收合并）。
3. **首轮定生死**：首轮对账判定为 GO（0 Critical / 0 Important）即直接进入审批流程，**严禁发起无意义的例行第 2 轮陪审**。
4. **次轮仅限返工验证**：仅当第 1 轮对账存在差集打回且回灌修改后，才允许且必须派发第 2 轮 Reviewer 进行返工对照核验（指定独占编号路径 `报告路径：.kilo/plans/review/<主计划文件名>-r2-shadow-plan.md`），逐字对账打回项是否真正闭环。
5. **每份回报严格校验**：每份回报必须过【物理在场】与四闸门校验：缺文件或只有上下文正文 = 该轮未完成，沿用原编号驳回重派覆盖旧报告（限 1 次）。
6. **能力前提**：只读取证/测试命令由受控执行通道（MCP 守卫双实例，main 与 subagent）恒按最严档（plan）与能力绑定代答，白名单只读/测试零弹窗、deny 形态硬拒。本机 ZCode 子代理已完成接线（frontmatter tools 物理剔除原生 Bash，改挂受控执行通道（plan-writer 绑 `mcp__plan-governor-main__exec_guarded_command`，两 Reviewer 绑 `mcp__plan-governor-subagent__exec_guarded_command`）；落盘通道改挂 `mcp__plan-governor-main__write_scoped_file`（原生 Write/Edit 已物理下线）），受控执行与零弹窗能力前提成立。未接线环境则退回单轮复审并登记原因。各代理铁律与父会话校验一个都不能省。
7. **总轮次硬熔断（2 波次上限，防无限收尾）**：
   - **波次定义**：首波派发恒为第 1 轮；其后仅当打回返工回灌后派发的对照核验计为第 2 轮。**同一复审链的总波次严禁超过 2**。
   - **计数域＝变更集指纹，不是计划文件名（仅限在途活跃链）**：轮次台账写在主计划头部"复审轮次"行（机读形态：`r1 已完成（报告 + 判定）；r2 已完成（…）；链熔断状态：未触发`），派发任何 Reviewer 前必须先更新该行。新计划若承接未决 E 清单的前缀变体（含 `-round2`、`-round3`、`-final`、`-microfix`、`-acceptance`、`-remediation`、`-premerge`、`-no-go-fixes` 等变体），或与当前在途未闭环计划的 Files 集合交集非空，判定为**同一复审链的延续**，序号必须接续链上最大值，严禁从 r1 重开；链上序号已达 2 时不得派发。**已交付（已 ExitPlanMode 且已完成或人类已明确终结/已合入分支）的历史归档计划自动出链**，严禁跨历史已完成任务把曾触及的同名文件（如 `README.md`、`package.json`）错误折算进新任务的复审轮次；新发起独立任务一律从 r1 独立计数。
   - **编号方言归一化**：`rA`-`rF` 字母编号、`r1a`/`r1b` 半号、`p1`/`p2`/`pr1`/`t2`/`x1` 等并行前缀，一律折算为轮次序数（`r2` 之后出现 `t2` 即判第 3 轮，已达上限）。
   - **同编号覆盖只许一次**：沿用原编号驳回重派（限产物缺失的技术性重派）以 1 次为限；第二次仍以同编号派发即按新轮次计入。
   - **禁读令让位于计数器**：Reviewer "禁读其他轮报告正文"不含**文件名列举**——允许用 `Glob` 列举 `.kilo/plans/review/` 与 `.kilo/plans/pr-review/` 的文件名核对链序数（不读正文）；发现序号已达上限时直接返回 `VERDICT: ESCALATE_TO_HUMAN` 并停止取证。
   - **人类终局**：父会话收到 `VERDICT: ESCALATE_TO_HUMAN` 后立即用交互通道呈报人类裁决，**严禁再派发下一波**；人类给出指示后按指示定稿计划，交付即终局。
   - 首波并发 Reviewer 数恒定为 1，总轮次严格 ≤2。
8. **派发参数字面量化**：分派 prompt 中除 `报告路径：` 标记沿用不变外，新增参数一律用全大写 ASCII 键值对并填入真实字面量——`MODE`、`BASE_REF`、`SCOPE_DIRS`、`PLAN_PATH`、`EVIDENCE_LOG`；严禁残留 `<...>`、`{...}` 待填形态（受控通道结构闸会拦下含花括号的命令，执行期补齐即失败）。审查模式默认 `MODE=single`（执行者受 Git 只读约束，改动恒为未提交态，即等于累积全貌）；仅当人类已提交中间产物时改传 `MODE=cumulative` 并给 `BASE_REF` 赋真实基线。

## 前置基线复跑铁律（pr-reviewer 分派前置闸门）

> **前置基线复跑铁律**：主会话派发 pr-reviewer 子代理之前，必须先经受控通道实跑一次基线验证命令（如 `npm test`），并将结果落盘至 `.kilo/plans/test-evidence/<时间戳>-<英文主题>-test-evidence.md`，其中 `<英文主题>` 必填，为被审查的提交区间或计划标识（如 `558bf8d-98ea158`）。证据文件开头必须有标题与说明段，至少包含：①基线对象（被审查的提交区间或计划标识）②实跑命令原文 ③退出码与关键输出 ④HEAD 与工作区状态 ⑤时间戳（开始/结束），与既有 evidence 八类字段口径对齐，不另造第二套字段名。即使既有基线证据在场，也必须复跑——基线证据仅证明「过去某时点可复现」，不证明「当前工作区可复现」。复跑结果与既有基线不一致时，禁止派发审查，先向用户报告差异。该前置证据路径须写入每个 pr-reviewer 子代理的分派提示词，作为其判定的统一参照系。（执行顺序规范：本闸门与 `zcode/AGENTS.md` 补充规程 1「派发前工作区卫生检查」叠加适用，顺序恒为：先运行 `git status --short -uall` 确认工作区无污染，再实跑前置基线命令并落盘证据）。

## 执行阶段闭环四大铁律（EXECUTING 硬闸门）

EXECUTING 阶段除四阶段状态机与授权语义外，另受以下四条铁律约束，与前述硬闸门**叠加适用**，不因权限档位变化（如计划批准后自动切 YOLO）而豁免：

1. **绝对忠于计划、技术事实至上与自洁契约**：业务改动的文件集合必须完全包含在主计划 Files 声明中；严禁借"顺手优化"改动计划未声明的业务源码与配置。主计划 Replacement 是实现基准而非不可更改的代码指纹——在已声明 Files 范围内发现计划草稿存在客观事实遗漏、路径错漏或未对齐代码库既有接口/平台能力时，执行者拥有自主纠偏权，以代码库客观事实为准就地修正并记录取证回执；纠偏仅限补正事实，不得突破安全硬闸或变更文件范围。收到复审意见时必须先核验技术真实性，严禁为迎合审查或规避打回计数而将事实正确的内容逆向回退为残缺或错误状态。
2. **任务分类自适应验红（代码类保留真红、文档类显式豁免）**：判定任务类别后决定验红策略。代码修改类（逻辑、状态、计算、时序、接口）：写入测试文件后首次运行若直接通过（Exit 0），或报错不属于四维语义真红（断言/比对失败、目标契约缺失型类型错误、被测入口主动抛出的业务领域异常、框架执行超时），**未见红严禁开工**：严禁修改业务代码，必须推翻重写测试用例直至稳定复现红灯；无法复现的转"非代码可测项豁免"，交人类裁决。纯文档/配置文字类（README、文档、注释、纯文本规范）：计划正文显式标注「本文档类任务经判定豁免 Red-Light Protocol（附非代码可测判定理由）」后免于代码验红，执行期直接进入常驻不变式（checks 套件）与静态语法核验，严禁伪造测试红灯、严禁作秀跑无关单测。
3. **终结交付门禁与在途打回上限**：业务修改转绿并通过静态契约检查后，严禁直接口头汇报完成；必须按计划预埋的字面量指令分派 `pr-reviewer-subagent-sp` 终验（无分派通道时降级为受控终端只读 `git status --short -uall` 与 `git diff` + 复跑测试自检，输出结构化报告交人类）。PR 审查在当前在途活跃链中**最多 1 次打回修复**；第 2 次复审仍判 NO-GO，立即终止自主循环呈报人类；历史已交付完成计划不污染新独立任务计数。
4. **Git 只读与自洁契约**：Git 写命令（`git add` / `git commit` / `git push` / `git reset` / `git checkout` / `git restore` / `git stash` / `git switch` / `git clean`）一律不执行，即便用户口头要求也只输出命令原文交人类在宿主终端执行。`pr-reviewer-subagent-sp` 判 NO-GO 且标注 `REWORK=HUMAN_CLEAN`（方案方向性错误，以区别局部实现缺陷 `REWORK=IN_PLACE`）时，严禁在污染现场叠加补丁，必须终止执行并提示人类在宿主终端按序处置：① 先运行 `git status --short -uall` 通读，区分 `??`（未跟踪）／` M`（未暂存改动）／`M `（已暂存）三态，确认清理半径只覆盖本计划 Files 声明；② 半径内若混有非本计划的在途改动，改用可逆通道 `git stash push -u -m "discarded-本计划标识"` 代替破坏性清理；③ 仅在确认无保留价值时，才执行 `git checkout -- .` 与 `git clean -fd`。

## 计划正文纯净性（计划≠审查报告≠台账）

计划是给执行者的变更指令，不是过程日志。**执行者会照搬计划**——计划正文里混入的"开发态"内容，会原样长进代码注释、README、runbook 等长期产物，变成只有流程参与者才懂的东西。约束如下（Writer 起草与回灌、Reviewer 审查执行同一标准）：

1. **可执行段落禁携过程元数据**：Anchor、Replacement、Files 清单、文档措辞终稿、命令里，严禁出现决策日期戳、轮次标记（"r1 回灌·E3"、"V1/V2/V3"）、闸门转达/台账/进度更新等内部行话。
2. **轮次溯源限定位置**：复审轮次、E 清单引用只允许出现在计划头部"复审轮次"行或文末独立"变更记录"节（显式标注"仅过程追溯，不随执行落盘"）。
3. **中性事实口径**：终稿只写"是什么、为什么这样设计"；决策历史归 Git 提交信息与计划文件自身。
4. **Reviewer 将纯净性列为核查项**：发现即 Important 打回；回灌时 Writer 对历史泄漏一并清理。

## 流程闸门承接（主会话硬闭环为唯一防线）

执法面为 MCP 双实例恒按最严档（plan）执法（白名单只读/测试放行，灰区与写命令拒绝）。因此：①`ExitPlanMode` 前计划必须已物理落盘——未落盘即由父会话自查驳回；②Task 分派 Writer/Reviewer 的落盘/独占报告路径（`报告路径：` 标记）缺失——靠父会话呈报前逐字核对分派 prompt；③子代理回报点名的报告不在盘——靠"子代理产物落盘校验闭环"节的【物理在场】校验驳回重派。产物落盘正规通道为子代理经受控写工具 `write_scoped_file` 写入（原生 Write/Edit 已物理下线）。上述任一环节**父会话校验都不得减省**——产物在场校验是流水线完整性唯一的机器防线。

## Rationalization 对照表（出现以下任一想法即触发上述规则，不得跳过）

| 借口 | 事实 |
| --- | --- |
| "我自己写计划更快更省一次分派" | 主会话内联计划等于绕回 ZCode 原生计划模式，Reviewer 无法独立复审，落盘与闸门全部失效。 |
| "原生计划模式已经够用了" | 原生模式产物在上下文，批准即脱缰执行；这正是本 skill 要物理阻断的场景。 |
| "Reviewer 已在上下文给了完整报告，不用写文件" | 没有物理文件就没有复核证据链，父会话无法鉴真，必须落盘后采纳。 |
| "子代理类型名差不多就行" | `plan-writer-subagent-sp`、`plan-reviewer-subagent-sp` 必须逐字精确，近似名会静默落到空代理。 |
| "我没识别到 plan-writer-subagent-sp" | 触发条件是"任务是否改变工作区状态"，不取决于识别与否；主代理必须枚举代理/模式清单逐字佐证，清单里有就必须分派。 |
| "宿主内置计划模式流程让主代理自己写" | 平台调度纪律优先于宿主内置流程。 |
| "计划已批准，直接执行不用再等" | 批准≠执行授权；ZCode 同对话 ExitPlanMode 批准永不构成执行授权。 |

| "计划模式拦住我了，等用户批准或退出计划模式再写" | 计划模式拦的就是主会话本人，属设计预期；被拦的唯一正确响应是分派 **对应子代理** 落盘，不是等待、退避或询问。 |

## 与其他技能的关系

- 本 skill 自足：不依赖任何其他技能即可完整运行；若环境中另装有承载同类授权语义的技能，以本 skill 为 ZCode 平台口径，两者语义一致不冲突。
- 领域 skill（例如 Python、API、前端）只能在 `EXECUTING` 阶段、且已获独立执行授权后使用。
- 测试驱动、调试、并行 agent 或执行计划类 skill 不能绕过本 skill 的计划审批和执行授权分离。
- 本 skill 生效对象仅两类：ZCode 主会话与 `plan-writer-subagent-sp`；其余子代理（含两型 Reviewer）整体忽略本 skill，且任何子代理都不得执行本 skill 的调度动作（见文首 `<SUBAGENT-GUARD>`）。
